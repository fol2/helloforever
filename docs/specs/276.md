# Spec: #276 Accounts and characters: who is who

Status: **lead design (22 Nov 2026); step 1 built, the rest waits for its answer.** The owner
asked for the BattleTag, to support more than one account, and for a way to tell characters
apart. The owner leaves the design to the lead (21 Nov 2026).

## 1. What is wrong now

- HelloForever keys a character `<name>-<realm>` (`docs/SCHEMA.md`, Character key). HelloLink
  keys `seen` and `looks` the same way.
- `UnitName("player")` has no family name. On WoW Forever two characters can share a first name
  when their family names differ. Then they share a key and write into one record.
- Since 20 Nov 2026 the client gives `""` for the realm. The realm no longer tells realms apart.
- Nothing says which account a character belongs to while the game runs.

## 2. Three levels of "who"

| Level | What names it | Readable? |
|---|---|---|
| Character | `UnitGUID("player")`: `Player-<server id>-<hex>` | **Seen**: `HelloLinkDB.fullNames` is keyed by it since HelloLink 0.8.1; two characters on this install, each its own GUID |
| Game account | The folder `WTF/Account/<account>/` that holds the saved files | Offline only: a reader takes it from the file's path. No addon call names it, and the account's own name is private |
| Battle.net account | The folder name's number (`<number>#<n>`), offline; the BattleTag (`BNGetInfo`, `C_BattleNet.GetAccountInfoByGUID`) in the game | The folder: seen. The BattleTag: **readable** (`BNGetInfo` and `C_BattleNet.GetAccountInfoByGUID`; seen 22 Nov 2026, its shape only) |

A GUID is unique for each character and holds the server's id, so it tells characters apart
across realms and accounts too. One Battle.net account can hold more than one game account
(a folder such as `<number>#1` is one of them). The saved files are already apart for each game
account: each folder has its own `HelloForever.lua` and `HelloLink.lua`.

## 3. The design

1. **Step 1, built (HelloLink 1.17.0, #278).** The probe's `account` line: the BattleTag's shape
   only, `BNConnected`, the GUID's form, and the realm that the game account gives (it can bring
   back the realm that `GetRealmName` lost). Game check: `plan/05`, section 28.
2. **Step 2: the GUID in every record (HelloForever 0.19.0, #280).** Needs no probe: the GUID is seen.
   - HelloForever writes `guid` into the record it uses at each login, with `guidBy`: how sure the
     claim is. `ns.Char` finds a record by its `guid` first.
   - With no such record, an old record (one with no `guid`) is claimed only with evidence:
     - `"fight"`: a stored fight of the record has a source with `isLocalPlayer` whose
       `sourceGUID` is this GUID (lossless capture keeps both). The importer can always check
       this; the addon checks it in the game only if decoding one stored fight is cheap enough
       (to measure first).
     - `"name"`: no fight decides, and this install has seen no other GUID with this name
       (HelloForever keeps the GUIDs it saw for each name from step 2 on, and `HelloLinkDB.fullNames`
       holds those seen before).
     - Else the record is not claimed: the character gets a new record (`guidBy = "new"`), under
       the name key when that key is free, else keyed by its GUID (lead decision, #280: keys stay
       readable for the usual case).
   - A character whose name key is free gets a new record under it (`guidBy = "new"`).
   - A record that holds another `guid` is never taken.
   - The `Name-` record that 0.18.4 split from a claimed record (same name, no `guid`, no
     `fightTrack`) gets the same `guid`, `guidBy = "split"` (its owner follows from the 0.18.4 rule,
     never from a fight of the other record) and `split = true`, so an importer that groups
     by GUID gets both, with their revisions and context blobs (`docs/SCHEMA.md`, Character key).
     `ns.Char` never writes to a `split` record: of the records with one GUID, it writes only to the
     one that is not `split`.
   - Old records keep their keys. An importer takes a record's `guid` as the character's identity,
     not the key, and reads `guidBy`; a record with no `guid` stays grouped by name, as now.
   - HelloLink 1.18.0: object 10 gains `"guid"`. New `seen` and `looks` entries go under the GUID, as
     `fullNames` does. Old entries stay under `<name>-<realm>`: a reader looks up the GUID first,
     in every account's files, then the old key (an old `looks` record moves to the GUID only at the next barber). An answer
     from an old key is not confirmed: two characters with one first name can share that key.
3. **Step 3: accounts, without the BattleTag in any file.** The saved files are already apart for
   each game account, one folder each. A folder's name of the form `<number>#<n>` (seen on this
   install) is how the client names a Battle.net account's game accounts: the part before `#` is
   then the same for each game account of one Battle.net account (**not checked**: it needs a second
   game account). A folder with a plain name (one on this install) stands alone. A reader that shows more than one account reads each folder's
   files and names an account by its folder. The BattleTag is stored nowhere and never goes onto
   the strip: `fol2/wow-data` copies the saved files into git, and grouping does not need it. If
   step 1 shows a BattleTag (it does: seen 22 Nov 2026) and the owner wants it shown, that is a
   decision of its own.
4. **Step 4: the realm: not possible.** Step 1 showed no realm (22 Nov 2026): `C_BattleNet` gives
   `nil` for `realmName`, `realmID` and `realmDisplayName`, and `GetRealmID` gives 0. The GUID's server
   id (`Player-<server id>-`) is the only realm-like value left; the name keys keep the realm saved
   before 20 Nov 2026 (0.18.4).

## 4. Rules

- A BattleTag, an account name, an account number or an e-mail address never goes into this
  repository, a test, a log or a saved file: tests use `FakeTag#1234`. A probe gives a BattleTag's
  shape, never its text.
- No record is merged into another (`docs/SCHEMA.md`, Character key: the parts of a record link to
  each other).
- Each step is its own pull request, with its game check in `plan/05`.

## 5. ACCEPTED limits (lead decision, review of #279, round 2)

- A claim with `guidBy = "name"`, and the `split` record that follows it, can be wrong when two
  characters with one first name used one install before step 2 and only one has logged in since.
  No such characters are on this install. `guidBy` makes the claim's certainty visible; an importer
  that needs certainty takes only `"fight"`, and checks the fights it uses one by one: a fight proves
  only its own local player (`isLocalPlayer`, `sourceGUID`), and a `"split"` record has no fight of
  its own behind its `guid`.

## 6. Not in this design

- Moving old records to GUID keys: an old record gains its `guid` and keeps its key.
- Reading the game account's name in the game: it is private, and no call is known for it.
