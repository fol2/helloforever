# Spec: #29 Live-state strip

A continuous strip of coloured squares that carries the character's live state out of the
running game, with a public format. The assistant (`docs/north-star.md`, priority 3) reads
it; any other program may. This repository owns the addon side and the format, and adds no
control of the game (`docs/owner-decisions.md`, 2026-11-12).

Status: draft for build. A line marked **Measured** was seen in the game on 12 Nov 2026
(`plan/05-assistant-link.md`). A line marked **To measure** is an assumption: section 9
lists the probe that settles it, and the build does not start before the probes ran
(`LESSONS.md`, "Probe a client capability in the game before building a feature on it").

## 1. What exists and what changes

HelloLink 0.0.2 draws one typed text for 30 s (format 0: finder, length, sequence, text,
Fletcher-16; squares of 6 UI units, 100 a row). This spec replaces it with format 1: an
always-on strip that holds a full picture of the fast state in every frame, and carries
larger or slower data in turns. The typed text becomes one object of format 1. Format 0 is
removed when format 1 ships; there is one reader and it is in this repository.

The strip stays in the separate addon `HelloLink`. HelloForever's capture never depends on
it, and a player can switch the strip off without losing fight data.

## 2. Decisions

1. **Every frame is whole.** A reader takes screenshots at its own pace and misses frames.
   So no frame depends on an earlier one: the fast state is complete in each frame.
   Change-only updates (deltas) are rejected for that reason.
2. **Slow data rides a carousel.** Each frame also carries one chunk of one larger object
   (bags, quest log, a typed question). A reader that misses a chunk gets it on the next
   turn. This gives the capacity that deltas were meant to give.
3. **Two colour levels a channel, three bits a square.** **Measured**: pure colours come
   back within 2 of 255, but blue came back as (0, 46, 255); a display's colour management
   moves the values in between, so more levels are not safe.
4. **Squares are sized in physical pixels**, 4 by 4 (**To measure**, probe P1; 8 by 8 if 4
   fails). **Measured**: a square of 6 UI units was 7.17 pixels wide, so UI units give no
   exact edge; another addon on the same Mac draws exact 8-pixel squares with
   `768 / physicalHeight / UIParent:GetEffectiveScale()` as the unit.
5. **Text is compressed** with the client's `C_EncodingUtil.CompressString` (Deflate) when
   the client has it (**To measure**, P4); else it goes uncompressed and the object says so.
6. **Unknown is a value.** In combat the client keeps some values secret from addons. A
   field the addon cannot read is marked unknown in the frame; the addon never guesses and
   never does arithmetic on a secret value (**To measure** which fields, P2).

## 3. Geometry

- The strip is 128 squares wide. At 4 pixels a square that is 512 pixels.
- Its top-left corner is at x = 0 and 16 physical pixels below the top of the game's UI.
  **Measured**: another addon draws a row in the top 8 pixels and hid format 0 there.
- Row 0 starts with the finder, the digits `4 2 1 7 0 6 3 5` (red, green, blue, white,
  black, yellow, cyan, magenta). A digit is `4*red + 2*green + blue`.
- The frame follows the finder, three bits a square, most significant bit first, row after
  row. Squares after the frame's end are black.
- A frame of version 1 is at most 5 rows (20 pixels high): section 5.
- Frame strata `TOOLTIP`, a high frame level. `/hlink strip on|off` shows and hides it;
  the setting is kept in the addon's saved variables. Hiding the whole UI hides the strip.

A reader must not assume the position: it finds the finder, measures the square from it,
and may then capture only the strip's rectangle (section 7).

## 4. Frame

All numbers are unsigned and big-endian. `uN` is N bits.

| Field | Type | Meaning |
|---|---|---|
| version | u8 | 1. A reader refuses a version it does not know. |
| seq | u16 | Goes up by one, wrapping, each time the frame's bytes change. |
| fastLen | u8 | Bytes of the fast block. A reader skips bytes it does not know at its end. |
| fast block | fastLen bytes | Section 5. |
| object | 5 bytes + chunk | Section 6. `objectId` 0 means no object: the 5 bytes are then all 0 and no chunk follows. |
| check | u16 | Fletcher-16 (two sums modulo 255, as in format 0) over every byte before it. |

Later versions only append fields to the fast block and add object ids. A change of the
finder, the bit order, the frame fields above or the meaning of an existing field is a new
version.

## 5. Fast block (version 1, 48 bytes)

`known` has one bit for each group below, in the order given, the first group in the most
significant bit. A group whose bit is 0 has all its bytes 0 and is unknown: unread, secret,
or not present (no target, no pet).

| Group | Fields | Bytes |
|---|---|---|
| | `known` u16 | 2 |
| clock | `time()` modulo 65536, u16 | 2 |
| health | health u24, health maximum u24 | 6 |
| power | power u24, power maximum u24, power type u8 (the client's power type number) | 7 |
| level | level u8, XP u24, XP for the level u24 | 7 |
| state | u8 of flags: in combat 128, dead or ghost 64, mounted 32, resting 16, AFK 8, casting or channelling 4, has target 2, has pet 1 | 1 |
| cast | spell id u24, tenths of a second left u8 (255 = more) | 4 |
| target | level u8 (0 = unknown, 255 = skull), health per cent u8, flags u8 (hostile 128, dead 64, elite 32, rare 16, tapped by another 8, a player 4), name hash u16 (Fletcher-16 of the name; the name itself is object 6) | 5 |
| pet | health per cent u8, happiness u8 (0 = not a hunter pet) | 2 |
| position | map id u16, x u16, y u16 (the map fraction times 65535), facing u8 (radians times 256 / 2π) | 7 |
| purse | money in copper u32, free bag slots u8 | 5 |

That is 48 bytes. With the 4 header bytes, 5 object bytes, a chunk of up to 160 bytes and
the check, a frame is at most 219 bytes: 584 squares after the 8 of the finder, inside 5
rows of 128.

## 6. Objects (the carousel)

| Field | Type | Meaning |
|---|---|---|
| objectId | u8 | Table below. 0 = none. |
| objectVersion | u8 | Goes up, wrapping, when the object's content changes. |
| chunkIndex | u8 | From 0. |
| chunkCount | u8 | Chunks in this version of the object. |
| chunkLen | u8 | Bytes that follow, 1 to 160. |

A reader joins the chunks of one `(objectId, objectVersion)` in index order. The joined
bytes start with one format byte: 0 = UTF-8 text, 1 = Deflate of UTF-8 text. The text is
JSON except for object 1.

| Id | Object | Content | Sent |
|---|---|---|---|
| 1 | question | The text the player typed with `/hlink send` (plain text, not JSON). | Until the reader acknowledges it through a slot (`ack = <objectVersion>`), or 60 s. |
| 2 | bags | Item id and count for each stack. | After a change, then every 60 s. |
| 3 | gear | Slot and item link for each equipped item. | After a change, then every 60 s. |
| 4 | quests | Id, title, state and objectives of each quest in the log. | After a change, then every 60 s. |
| 5 | auras | Spell id, stacks and seconds left for the player's buffs and debuffs. | After a change. |
| 6 | target | Name, creature type and classification of the target. | When the target changes. |
| 7 | place | Zone and subzone names. | When they change. |

The addon sends one chunk for 0.2 s, then the next waiting chunk; a waiting question goes
first. With nothing waiting, `objectId` is 0 and the strip stands still.

## 7. The reader

`tools/hellolink_strip.py` stays standard-library Python and gains:

- `watch [--json]`: locate the strip in a screenshot of every display once, then capture
  only its rectangle (`screencapture -R`) in a loop, and print one line for each new `seq`.
  When a capture does not decode twice in a row, locate again. No screenshot is kept.
- `read --screen | --image`: one frame, as now.

The reader checks the finder, the version, the lengths and the check before it reports
anything, and reports a frame only when it decodes whole. It joins object chunks and
acknowledges a question by writing a slot (`tools/hellolink.py`).

Capturing only the rectangle is faster and keeps the rest of the screen out of the
program. **Measured**: a full capture of three displays and a decode take about 0.7 s.
**To measure** (P3): the rate with a rectangle.

## 8. Limits and non-goals

- No control of the game: nothing here presses a key, casts or moves. The strip only shows
  what the addon can read; a reader only looks.
- No memory reading, no packet reading, nothing hidden from the player: the strip is on
  screen, and the player can switch it off.
- The strip shows character state on screen. It is in any screenshot or stream the player
  shares; `/hlink strip off` before sharing.
- Cost: the addon rebuilds the frame at most 10 times a second and recolours only squares
  that changed. Target: under 0.2 ms a rebuild. **To measure** in the build's own test.
- Not in version 1: cooldowns, action bars, group members, the map of nearby units.

## 9. Probes before the build

Each is a slash command in `HelloLink` and, where needed, a mode of the reader. Lua only,
so they hot-load with `/reload`.

| Probe | Command | Settles |
|---|---|---|
| P1 | `/hlink probe squares`: four test rows of a known pattern at 8, 4, 3 and 2 pixels a square. The reader reports the bit errors of each row. | The square size of decision 4. |
| P2 | `/hlink probe secrets`: for each API the fast block reads, whether the value is secret now. Run out of combat and in combat. | Which groups are unknown in combat (decision 6). |
| P3 | `tools/hellolink_strip.py watch` against P1's strip, counting frames a second. | The reader's rate; whether 0.2 s a chunk is right. |
| P4 | `/hello selftest` already lists `C_EncodingUtil.CompressString`. | Decision 5. |

## 10. Acceptance (from the issue)

- This document: square size, frame layout, field table with types and units, updates,
  compression, sequence and loss handling, versioning, position. Sections 2 to 6.
- A test that round-trips every field of the fast block and a chunked object through an
  image, as `tests/hellolink_strip_test.lua` does for text; and the reader's refusals
  (unknown version, bad lengths, bad check) in `tests/hellolink_strip_test.py`.
- In the game: `watch` follows a minute of play, and every frame it reports passed the
  check; fields marked known agree with what the game shows.
