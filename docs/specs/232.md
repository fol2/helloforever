# Spec: #232 Strip format 3

Status: **approved design; built in steps** (`docs/owner-decisions.md`, 2026-11-21). Each part
names the measure that must come first (LESSONS: probe a client capability before a feature
stands on it). A line marked **Measured** comes from format 2's records and probes (#213,
`docs/specs/213.md`, `plan/05` sections 26 and 27); a line marked **Estimate** is a number to
check.

## 1. The owner's aims, in order

The owner, 21 Nov 2026, after the proposal: "Sure let's do format 3. For the game loss frame.
Probably the game itself frozen. Due to computer not good. I always got “stuck” in game. So
format 3 need 2 things to support, 1 is least compute possible don't drag down the game
performance further, and if loss frame, still able to have good recovery. Plus more bandwidth
and more comprehensive info".

1. **Least work in the game.** The game already stops for moments on this computer. The strip
   must not add to that.
2. **Good recovery from lost frames.** A frame that no capture got must cost the reader as
   little as possible, and the reader must be whole again soon after.
3. **More bandwidth.**
4. **More data.**

When two aims pull apart, the lower number wins. The proposal's 20 frames a second and its
Reed–Solomon parity are dropped for that reason (section 8).

The owner sees the game stop ("stuck") on this computer. A stop of the whole machine fits the
stops of the captures. It is the leading explanation of the lost frames, **not proven**: the
ring of draw times set beside a record of play decides it (step 3). Format 3 does not wait for
that answer, because its recovery (section 4) works whatever the cause.

## 3. Where format 2 spends its work in the game

| Work | When | Its cost grows with |
|---|---|---|
| Read the state (about 20 client calls) | each 0.1 s | the calls |
| Build an object (Lua strings, JSON, the client's deflate) | on a change | the object's text |
| Pack the frame and its check | each frame | the bytes |
| Paint: one `SetColorTexture` a square whose colour changed | each new frame | the squares that changed |

The paint is the part that grows with bandwidth. At 6 bits a square, a byte that changes
costs about 1.33 calls. Format 2's frame changes length between a keyframe and a delta, so
everything after the change moves and is painted again even when its bytes are the same.

## 4. The design

### A. Recovery: every frame stands alone

- **No deltas.** The fast block holds the full state, absolute, in every frame. A lost frame
  costs only its 0.1 s; the next frame captured is whole. (Format 2: up to 2.58 s.)
- **A directory in every frame**: one byte a slow record, its version modulo 256. After a gap,
  the first frame tells a reader which records it holds old.
- **An event ring in every frame**: the last 8 events (loot, XP, money, a quest step, a level,
  a death), each with a counter. A gap of fewer than 9 events loses none; when the counter
  jumped by more, the reader reports how many it lost.
- **Slow records go changed-first**, then in a slow refresh round, as format 2's carousel.
- **A stall sends again.** When the addon's update comes more than 0.25 s after the one
  before, the game stopped. The addon queues again the records whose chunks were up in the
  second before the stop. A stop of the game is exactly when a capture is most likely lost.

**Target**: the fast state and the events whole in the first frame captured after a gap; a
record changed during the gap whole within 1 s (**Estimate**, measured at step 5).

### B. Least work

- **One clock.** A frame is drawn at most once a dwell, on one tick (`now >= nextFrame`, then
  `nextFrame = now + dwell`). Format 2 draws on two clocks (the carousel and the fast read);
  one clock makes a frame shorter than the dwell impossible by construction.
- **10 frames a second stays.** Twice the rate is twice every cost a frame, and a stopped game
  stops both rates alike.
- **A fixed layout.** The fixed part comes first, at fixed squares: the head, the fast block,
  the event ring, the directory. The chunk comes last. A value that does not change paints
  nothing; a chunk's length moves nothing before it.
- **Binary records, no text.** The addon packs schema records (part E) into byte tables it
  keeps: no JSON, no deflate, no new string or table a frame. Text stays only where it is text
  (a quest's objective), sent by hash and a slow round.
- **A paint budget.** At most a set number of squares are painted again a frame; a chunk is
  only as long as the budget allows. The number starts at format 2's largest frame (212 bytes,
  about 290 squares) and is set by the perf test (rule 4).
- **Back off when the game is slow.** While the game's frame rate is under 20 a second, a new
  chunk goes up every second dwell; the fixed part still goes every dwell. **Measure first**:
  the client gives `GetFramerate` (a probe).
- **Deeper colour is also a saving.** At 9 bits a square a byte costs about 0.89 calls, not
  1.33 (part C below).
- **The reader is on the same computer.** Its work also takes from the game. The capture keeps
  to the strip's rectangle and a set rate; the decoder asks for no memory a frame. The
  reader's processor use (2.2 % on 21 Nov 2026, `ps`) is measured at each step and must not
  grow.

### C. More bandwidth

| Lever | Gain | Measure first |
|---|---|---|
| Lanes: 1 to 4 rows of 1-pixel squares, the frame's bytes along lane 1, then lane 2 | up to 4× the squares | A probe draws 4 lanes of a known pattern; the reader counts wrong squares at scale 1 |
| Deeper colour: the capture in the display's colour space, then 8 levels a channel | 6 to 9 bits a square (1.5×) | `/hlink probe depth 6 1` and `8 1` with the capture in the display's colour space: 0 wrong and the nearest colours at least 12 apart over an hour |
| Binary records in place of JSON and deflate | smaller objects | Step 1, offline |

The lane count and the bits a square are in the square after the depth square, so a reader
knows the layout before the frame. With 512 colours the palette goes in a lane of its own,
once a second. The ceiling is for bursts (a quest list, a raid, a merchant); the paint budget
keeps steady play small.

### D. More data

Sent as schema records, in this order (the assistant's needs first):

1. **Units**: the target, target of target, focus, pet's target, party, and in a raid 40
   members: level, class, flags, raid mark, target, threat. Health through the client's colour
   curves, in a lane of its own, once a raid shows the curves work for raid units. The
   target's and the focus's cast, once a probe shows the client gives another unit's cast.
2. **Action bars as bit sets**: usable, in range, active, on the global cooldown, for 48
   slots: 24 bytes. The client gives these in combat (**Measured**, the probe of #213).
3. **The event ring** (part A).
4. **Windows**: merchant, loot, quest dialogue, flight map.
5. **The character**: talents, spellbook, professions and recipes, reputations, on change.

Not sent: chat, whispers, friends, guild (no social data), and anything the client keeps
secret (health and power numbers; auras in combat: format 2's 253).

| Item | Scene to see it in |
|---|---|
| Units of a raid, their curves | A raid group (the owner's) |
| Another unit's cast | A creature that casts (the probe's `unit` lines) |
| Action bars in combat | A fight |
| Windows | A merchant, a loot window, a quest dialogue, a flight master |
| The character | A talent and a profession window open, a reputation change |
| The event ring | A fight with loot and XP, a quest turned in |

### E. One schema in Rust; one decoder

Every record is described once, in a Rust crate (`reader/hellolink-format`): its fields, their
types (unsigned of n bits, signed, a reference `kind:id:hash`, a short text with a length, a
list) and their order. From it a Rust tool makes the addon's encoder tables (Lua: for each
record, its field list and bit widths), the field tables of the docs, and test vectors. A
change to a record is a change to the schema; the Lua tables and the decoder cannot drift
apart. Hand-written vectors stay (LESSONS: check an encoder against bytes written by hand).

The same crate is the decoder: bytes in, records out, no screen, no file, no clock. The reader
(`hellolink`) uses it, and so can the local program's Rust engine. The capture stays the small
Swift tool, started by the reader as now. The addon stays Lua: the game runs only Lua.

## 5. Rules

1. **Probe first.** A part is built only after its probe shows the client and the capture
   allow it.
2. **The reader's interface does not change.** The same command line and the same `/state`
   and `/events` shapes, with fields added only.
3. **Rust outside the game, Lua inside it.**
4. **No more work in the addon than format 2.** `tests/strip_perf_test.lua` plays the same
   script in format 2 and format 3 and holds, a second: memory, client calls, squares painted
   and Lua time (a raid of 40 included). Format 2's memory there is 11.2 KB a second.
5. **Formats 1 and 2 stay readable.** The depth square names the format.
6. **No social data.**

## 6. The frame of format 3 (sketch)

| Part | Where | Changes when |
|---|---|---|
| Finder, depth square, layout square (lanes, bits a square), session | lane 1, fixed squares | the session or the layout |
| Palette | lane 1, fixed (64 colours), or a lane of its own (512) | never in a session |
| Head: seq, dwell, flags, the chunk's length | fixed | every frame (the seq) |
| Fast block, absolute | fixed | the state |
| Event ring, 8 slots | fixed | an event |
| Directory, a byte a slow record | fixed | a record's version |
| Check of the fixed part | fixed | every frame |
| Chunk: record id, version, index, count, bytes, its own check | last | a new chunk |

Two checks: a reader keeps the fixed part of a frame whose chunk did not come whole.

## 8. Not in format 3

- **20 frames a second.** It doubles every cost a frame (aim 1) and does not help when the
  game stops.
- **Reed–Solomon parity in the frame.** No frame of 28,063 failed its check: frames are lost
  whole, and a parity repairs only wrong squares. Its Lua work would come every frame.
- **Keyframes for two dwells, XOR parity frames.** Part A's absolute fast block, directory and
  sending again after a stall recover for less.
- Window capture or an invisible strip (the owner plays full screen; the strip must show).
- A request channel from the reader to the addon faster than the slot files.
- Social data.
